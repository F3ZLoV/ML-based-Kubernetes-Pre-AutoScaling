### 3.5 해석 — ramp 리드 타임 우위가 재현되지 않은 이유

GKE에서 GRU는 한 번의 scale-out에 평균 **5.59개**, HPA는 **3.18개**의 파드를 추가했습니다(논문 환경에서는 3.24 vs 3.14로 거의 같음). 리드 타임은 "요청된 파드가 **모두** Ready가 될 때까지"를 재는 이벤트 단위 지표라서, 한 번에 많이 늘릴수록 길어집니다. 이 관계는 두 환경 모두에서 확인됩니다.

| | 이벤트 수 | 배치 크기 ↔ 리드 타임 상관 | 파드 1개 추가당 |
|---|---|---|---|
| 논문 원본 (DOKS) | 545 | r = 0.56 | +0.29 s |
| GKE 재실험 (ramp) | 39 | r = 0.64 | +0.14 s |

GKE에서 배치 크기 차이만으로 (5.59 − 3.18) × 0.14 ≈ **0.34초**가 설명되며, 이는 관측된 격차 0.55초의 대부분입니다. 즉 GKE에서 GRU는 "느리게" 늘린 것이 아니라 **더 큰 단위로 늘렸기 때문에 이벤트당 시간이 길게 측정**된 것입니다. 논문 Fig 3(Aggressiveness–Lead Time 산점도)이 이 관계를 이미 보여주고 있습니다.

이 결과가 뜻하는 바:

- **논문의 ramp 수치 자체는 정확합니다**(1장). 다만 "GRU가 ramp에서 리드 타임을 15.1% 단축"은 **두 스케일러의 배치 크기가 비슷했던 DOKS 환경에서의 결과**이며, 다른 환경으로 일반화되지 않았습니다.
- 사용자 체감 지표 중 **P99 개선은 두 환경에서 일관되게 재현**(21~26%)되었습니다. P95는 집계 방식에 따라 방향이 달라 판단을 보류합니다.
- 논문이 스스로 "0.24초 변동 이내의 차이는 유의한 우열로 해석하지 않는다"고 범위를 좁히고, 비교 대상을 "동일 안전 장치 아래의 운영 결과"로 한정한 것은 이런 환경 의존성에 대한 적절한 방어입니다.

## 4. 후속 재실험 (2~4차) — 1차의 "GRU 0.55초 느림" 원인 확인

1차 GKE 재실험의 리드 타임 불일치를 가리기 위해, 모델·설정·부하(ramp)는 그대로 두고 **실행 절차만** 바꿔 세 번 더 실험했습니다. 매번 새 클러스터(e2-standard-2 × 3, 서울)를 만들고 끝나면 삭제했습니다.

| 회차 | 바꾼 것 | run |
|---|---|---|
| 2차 | GRU 직전마다 추론 서버 재시작 + HPA·GRU 교대 실행 | HPA 3 · GRU 3 |
| 3차 | 교대 실행 유지, GRU를 재시작한 것 / 안 한 것으로 나눠 재시작 효과만 비교 | HPA 3 · GRU 6 |
| 4차 | A: 1차 절차 그대로 (서버 한 번만 띄움, HPA×3 → GRU×3 연속) · B: 교대 실행. 파드별 준비 시각(ms)과 노드 CPU도 기록 | HPA 6 · GRU 6 |

### 4.1 리드 타임

| | HPA | GRU | GRU − HPA |
|---|---|---|---|
| 1차 | 2.26 | 2.80 | +0.55 |
| 2차 | 2.24 | 2.18 | −0.06 |
| 3차 | 2.05 | 2.20 | +0.16 |
| 4차 A (1차 절차 그대로) | 2.13 | 2.24 | +0.10 |
| 4차 B (교대) | 1.90 | 2.23 | +0.33 |
| **2~4차 합산** (HPA 12 · GRU 15 run) | **2.08** | **2.21** | **+0.13** |

(초, scale_out 이벤트 pooled 평균)

- **1차 절차를 그대로 재현해도 0.55초 느림은 나오지 않았습니다**(4차 A, +0.10초). 실행 순서는 원인이 아닙니다.
- **추론 서버의 이전 상태는 주원인이 아닙니다.** 부하 발생기와 연결이 끊기면 `ai_metrics_api.py`가 마지막 값을 유지해 run 사이 대기 시간에 "10명 → 14개" 같은 응답을 60회 이상 반복하지만, 2~4차에서는 run 사이 강제 리셋 뒤 새 부하가 들어오면 바로 갱신되어 측정에는 영향이 없었습니다. 3차에서 재시작한 GRU 2.21초, 재시작하지 않은 GRU 2.19초로 같았습니다. 1차에서는 이 상태가 시작 직후 출렁임으로 이어져 약 0.1초에 기여했습니다(아래).
- **회차마다 생기는 작은 차이는 배치 크기 때문입니다.** GRU는 주로 4~8개씩, HPA는 1~3개씩 늘립니다. 같은 수만큼 늘린 이벤트끼리 비교하면 차이가 없습니다.

| 한 번에 늘린 수 | 1개 | 2~3개 | 4~5개 | 6~8개 |
|---|---|---|---|---|
| HPA | 1.85 (22) | 2.05 (88) | 2.59 (19) | 2.48 (5) |
| GRU | 1.53 (9) | 2.17 (10) | 2.27 (40) | 2.57 (25) |

(초, GKE 1~4차 전체, 괄호는 이벤트 수)

- 4차 파드 기록 기준으로 파드 1개가 생성되어 Ready가 되기까지는 **HPA 1.65초 · GRU 1.64초**(A 블록)로 같았습니다. 클러스터가 파드를 띄우는 속도에는 차이가 없습니다.
- 1차의 0.55초는 **큰 원인 하나가 아니라 작은 요인이 겹친 결과**로 봅니다.
  - **배치 크기**: 1차에서 GRU는 이벤트당 5.59개, HPA는 3.18개를 추가했습니다. 3.5절의 파드 1개당 +0.14 s 관계로 약 **0.34초**가 설명됩니다.
  - **시작 직후 출렁임**: 1차 GRU run 2·3은 추론 서버의 이전 상태 때문에 시작 직후 2 → 14 → 1개로 출렁였습니다. 이 이벤트를 빼면 GRU 리드 타임은 2.80초에서 2.70초로 줄어 약 **0.1초**입니다. 1차 GRU run의 연결 실패(69~136건)가 2~4차(최대 19건)보다 많았던 것도 이와 일치합니다. 3차에서는 run 사이 강제 리셋으로 이 상태가 측정 전에 사라져 재현되지 않았습니다.
  - 나머지는 run 간 흔들림 범위입니다.
- **그날 클러스터 상태는 원인이 아닙니다.** GCP Cloud Logging의 Kubernetes 이벤트로 확인한 결과, 21:49~22:01에는 노드 3대 모두에서 파드가 배치된 뒤 시작되기까지 5~6.5초가 걸려(앞뒤 시간대 1~2초) 클러스터 전체가 일시적으로 느렸습니다. 이미지 재다운로드·경고 이벤트·GCP 관리 작업 기록은 없었고, 이 클러스터는 실험 시작 2분 전(21:23~21:29)까지 노드 풀을 교체하고 있었습니다. 다만 이 구간의 run(HPA run 3, GRU run 1)은 처음부터 run 4로 대체해 집계에서 빠져 있으며, 집계된 GRU run 시간대(22:10, 22:21, 23:15)의 파드 시작 시간은 1.1~1.4초로 HPA run 4(1.1초)와 같았습니다.

### 4.2 측정 도구의 지연

`lead_time_tracker_v2.py`는 0.5초 간격으로 상태를 확인하므로, 4차 파드 기록과 비교하면 이벤트마다 **0.3~0.5초 길게** 측정됩니다(4차 A: HPA 2.13 vs 1.69초, GRU 2.24 vs 1.81초). 이 지연은 run마다 최대 0.16초 달라, GKE에서는 회차 간 GRU − HPA 차이가 논문의 변동 기준 0.24초를 넘기도 합니다(4차 B +0.33초).

### 4.3 응답 속도

| | P95 (ms) | P99 (ms) | 파드 1개 추가당 (s) |
|---|---|---|---|
| 2~4차 HPA | 313 | 430 | 0.85 |
| 2~4차 GRU | 240 (−23%) | 335 (−22%) | 0.47 |
| 4차만 HPA / GRU | 220 / 213 | 323 / 302 | 0.82 / 0.50 |

GRU의 꼬리 지연 개선은 2~4차 합산에서도 유지되지만, 4차처럼 HPA도 빠른 환경에서는 차이가 거의 없습니다. 파드 1개 추가당 시간은 논문·1~4차 다섯 번 모두 GRU가 짧았습니다.

## 5. 확장 실험 — 통제된 3개 시나리오 × 4개 스케일러

논문에서 유형별 비교의 근거인 통제된 3개 시나리오(general spike, step, ramp)를 GKE에서 스케일러마다 6회(run 101~106) 실행했습니다. 1단계(10/12)는 HPA·GRU를, 2단계(10/13)는 LSTM·Ensemble을 실행했고, 단계마다 새 클러스터(e2-standard-2 × 3, 서울)를 만들어 끝나면 삭제했습니다. 라운드마다 시나리오를 돌아가며 두 스케일러를 교대로 실행하고, ML 실행 직전마다 추론 서버를 해당 모델로 재시작했습니다.

판정은 run 단위 값의 Welch t-검정(양측)입니다. **확장 시작**은 부하 시작(사용자 수 > 0)부터 3 replica 이상으로 처음 늘린 이벤트의 시작까지 걸린 시간으로, 같은 계산을 논문 데이터에 적용하면 논문 Table 6의 Scale-out Onset 값(40.7 / 3.9초 등)이 그대로 나옵니다.

### 5.1 결과 (각 6 run 평균)

| 시나리오 | 지표 | HPA | LSTM | GRU | Ensemble |
|---|---|---|---|---|---|
| general spike | P95 (ms) | 748 | 2,783 ▲ | **253** ▼ | 957 ▲ |
| | 확장 시작 (s) | 32.0 | 63.7 ▲ | **7.2** ▼ | 22.1 ▼ |
| | 리드 타임 (s) | 2.16 | 5.06 ▲ | 2.65 | 3.17 ▲ |
| step | P95 (ms) | 142 | 430 ▲ | 122 | 357 ▲ |
| | 확장 시작 (s) | 31.7 | 24.2 ▼ | **7.5** ▼ | 19.9 ▼ |
| | 리드 타임 (s) | 1.96 | 2.81 ▲ | 2.48 ▲ | 2.94 ▲ |
| ramp | P95 (ms) | 180 | 527 ▲ | 172 | 313 ▲ |
| | 확장 시작 (s) | 38.2 | 38.1 | **22.1** ▼ | 27.8 ▼ |
| | 리드 타임 (s) | 1.86 | 2.36 ▲ | 2.09 | 2.51 ▲ |

(▲/▼ = HPA보다 의미 있게 큼/작음, p < 0.05. P99·에러율·Aggressiveness와 모든 p값은 `analyze_ext2_output.txt`)

- **GRU만 HPA보다 나았습니다.** general spike에서 P95 −66%(p < 0.001), P99 830 → 343 ms(p < 0.001). step·ramp에서는 HPA도 응답이 빨라 GRU와 차이가 없었습니다(p = 0.18, 0.81).
- **LSTM·Ensemble은 세 시나리오 모두 P95·P99가 HPA보다 나빴습니다**(P95 p ≤ 0.005). 논문(DOKS)에서 LSTM이 HPA보다 나쁘고 Ensemble이 HPA와 차이가 없었던 것과 방향이 같고, GKE에서 더 뚜렷합니다.
- **일찍 시작한다고 이득이 생기지는 않습니다.** Ensemble은 HPA보다 10~12초 먼저 확장을 시작했지만 이벤트당 HPA의 2~4배(5.6~12.1개)를 늘리며 응답이 더 나빠졌습니다. LSTM은 general spike에서 오히려 HPA보다 32초 늦게 시작했습니다.
- **리드 타임은 이벤트당 추가 개수를 따라갑니다.** GRU의 리드 타임이 HPA보다 0.2~0.5초 긴 것은 한 번에 2배 이상 늘리기 때문이며(4.1절), 확장 시작은 GRU가 모든 시나리오에서 먼저였습니다.

### 5.2 진행 중 발생한 문제와 조치

- 1단계 중 실험용 PC가 절전으로 들어가 WSL이 종료되어 GRU ramp run 106이 끊겼습니다. 해당 run만 다시 실행한 뒤 클러스터를 삭제했고, 이후에는 절전 방지와 세션 분리 실행(`setsid`)을 적용했습니다.
- 2단계 중 PC가 재부팅되어 Ensemble ramp run 106이 끊겼습니다. 같은 방식으로 이 run만 다시 실행했습니다. 두 재실행 run은 `podlog/`에 기록되지 않았습니다.
- HPA·GRU(1단계)와 LSTM·Ensemble(2단계)은 같은 사양으로 다시 만든 클러스터에서 날짜를 달리해 측정했습니다. 단계 안에서는 교대 실행했지만, 단계 사이 비교에는 이 차이가 포함됩니다.

## 6. 재현 방법

```bash
# 1) 수치 검증 (클러스터 불필요)
python verification/verify_paper.py

# 2) GKE 재실험 (WSL, gcloud 로그인 후)
export PROJECT_ID=<gcp-project-id>
./scripts/gke_start.sh                       # e2-standard-2 × 3, KEDA 2.16.1, TicketBench 배포
bash verification/run_scripts/setup_repro.sh # 원본을 덮어쓰지 않는 작업 폴더 ~/repro_gke
#   추론 서버:  cd server && MODEL_TYPE=gru ../venv/bin/python -m uvicorn ai_metrics_api:app --port 5005
#   터널:      ngrok http 5005
bash verification/run_scripts/run_repro.sh    <ngrok-url>            # ramp HPA×3, GRU×3
bash verification/run_scripts/run_periodic.sh gru      <ngrok-url>  # periodic GRU×3
bash verification/run_scripts/run_periodic.sh ensemble <ngrok-url>  # (서버를 MODEL_TYPE=ensemble 로 재시작 후)
./scripts/gke_stop.sh                        # 반드시 삭제

# 3) 재실험 분석
python verification/analyze_repro.py

# 4) 후속 재실험 2~4차 (작업 폴더 ~/repro_gke2)
bash verification/run_scripts/setup_repro2.sh
bash verification/run_scripts/run_repro2.sh <ngrok-url>   # 2차: 서버 재시작 + 교대
bash verification/run_scripts/run_repro3.sh <ngrok-url>   # 3차: 재시작 유무 비교
bash verification/run_scripts/run_repro4.sh <ngrok-url>   # 4차: 1차 절차 재현 + 파드 기록
python verification/analyze_round4.py                     # 4차 분석 (파드 기록 기준 리드 타임 포함)

# 5) 확장 실험 (작업 폴더 ~/repro_gke2, 단계마다 클러스터 새로 생성)
bash verification/run_scripts/run_ext1.sh <ngrok-url>     # 1단계: HPA·GRU × 3개 시나리오 × 6회
bash verification/run_scripts/run_ext2.sh <ngrok-url>     # 2단계: LSTM·Ensemble × 3개 시나리오 × 6회
python verification/analyze_ext2.py                       # 4개 스케일러 비교 (확장 시작 · P95 · 리드 타임 등)

# 6) 논문 Fig 1 (전체 구조도) 다시 그리기
python verification/make_fig1.py fig1.png
```
